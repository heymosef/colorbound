# Batch 5 Legacy Removal Readiness

This document defines when it is safe to execute the Batch 5 cleanup that removes
the temporary compatibility bridge for legacy `blackRange` / `whiteRange` /
`curve` payloads.

## Why Batch 5 Is Deferred

The current release intentionally keeps compatibility for:

- pre-v3 browser `localStorage` state
- legacy shared palette payloads sent to the Supabase function
- older shared payload shapes that may still be deserialized by the client

Removing that support too early could strand returning users on stale browser
state or break links generated by older clients.

## Go / No-Go Checklist

Batch 5 is safe only when all items below are true:

1. The compatibility-bridge release has been live in production for at least one
   normal return cycle.
   Recommended default: 4 weeks, or longer if users tend to return
   infrequently.
2. We have reviewed legacy-compat logs for at least 14 consecutive days after
   that release window.
3. Legacy local-storage migrations are effectively gone.
   Default threshold: 0 events for 14 consecutive days.
4. Legacy share payload acceptance is effectively gone.
   Default threshold: 0 events for 14 consecutive days.
5. Support/product are comfortable invalidating very old browser state and very
   old share payloads if any still exist.
6. Client and server cleanup can ship together in the same release.

If any item is false, Batch 5 is a no-go.

## Instrumentation To Watch

The codebase emits searchable compatibility logs with the prefix
`[legacy-compat]`.

Watch for these event names:

- `local-storage-v1-migration`
- `local-storage-v2-migration`
- `server-accepted-legacy-palette`
- `client-deserialized-legacy-share-payload`

## How To Review Readiness

1. Check production browser/session logging for the `local-storage-*` events.
2. Check Supabase function logs for `server-accepted-legacy-palette`.
3. If client logs are available, check for
   `client-deserialized-legacy-share-payload`.
4. Confirm all three streams are at or near zero and stable for the full review
   window.
5. Confirm the next release can remove client and server compatibility together.

## Batch 5 Scope Reminder

When the checklist is green, Batch 5 should:

1. Delete `src/app/lib/legacy-palette-compat.ts`.
2. Remove v1/v2 migration support from `src/app/lib/local-storage.ts`.
3. Remove legacy field acceptance from:
   - `src/app/lib/share-serialization.ts`
   - `supabase/functions/server/index.tsx`
4. Delete tests that only cover legacy compatibility.
5. Keep only the canonical palette shape:
   - `name`
   - `group`
   - `hue`
   - `chroma`
   - `lightness50`
   - `lightness950`
   - `isNeutral`

## Owner Checklist For The Follow-Up PR

- Re-run `npm run build`
- Re-run `npm test`
- Verify old local-storage blobs are rejected cleanly
- Verify old legacy share payloads are rejected cleanly
- Update this document or delete it once Batch 5 has shipped
